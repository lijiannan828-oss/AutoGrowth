## 问题根源

### 1. 缺乏并发控制机制 ⚠️ **核心问题**

**当前实现**:
- 每个 job 独立触发，没有全局并发控制
- 每个 job 都尝试启动 50 个并行任务
- 没有检查其他 job 的运行状态

**问题**:
- 多个 job 同时运行时，总并发数可能超出配额
- 没有排队机制，直接争抢资源
- 可能导致 OOM 和任务失败

### 2. 内存管理不足 ⚠️ **次要问题**

**当前配置**:
- 每个任务: 4Gi 内存
- 没有根据实际需求动态调整
- 没有考虑并发情况下的内存压力

**问题**:
- 固定内存分配可能不足
- 并发时内存压力更大
- 没有监控和调整机制

## 解决方案

### 方案 1: 实现全局并发控制 ✅ **推荐**

**实现思路**:
1. 在触发 job 前，检查当前运行的 job 数量
2. 如果超出限制，等待或排队
3. 使用 Firestore 或 Cloud Tasks 实现队列

**实现步骤**:
```python
# 在 relay.py 中
def _check_concurrent_jobs():
    """检查当前运行的 job 数量"""
    # 查询 Cloud Run Jobs API 或 Firestore
    # 返回当前运行的 job 数量

def _trigger_cloud_run_job(job_id, drama_name):
    """触发 job，带并发控制"""
    # 检查并发数
    current_jobs = _check_concurrent_jobs()
    max_concurrent = 1  # 最多同时运行 1 个 job
    
    if current_jobs >= max_concurrent:
        # 排队等待
        _enqueue_job(job_id, drama_name)
        return "queued"
    
    # 触发 job
    _do_trigger_job(job_id, drama_name)
    return "triggered"
```

### 方案 2: 使用 Cloud Tasks 队列 ✅ **推荐**

**实现思路**:
1. 使用 Cloud Tasks 作为队列
2. 设置并发限制
3. 自动排队和调度

**优点**:
- 自动处理并发控制
- 支持重试和错误处理
- 更好的可观测性

### 方案 3: 动态调整 parallelism ⚠️ **临时方案**

**实现思路**:
1. 根据当前运行的 job 数量动态调整 parallelism
2. 如果有其他 job 运行，减少 parallelism

**缺点**:
- 不能完全解决问题
- 仍然可能超出配额
