## 3. 根本原因分析

### 3.1 内存问题

**证据**:
- `exit=-9` 是典型的 OOM 信号
- 失败发生在处理了大量文件（185 个）之后
- 失败的文件都是较大的视频文件（~120MB）

**可能的内存泄漏点**:
1. **Python 进程内存累积**: 处理了 185 个文件后，Python 对象可能没有及时释放
2. **FFmpeg 内存峰值**: FFmpeg 使用 8 线程处理，可能在某些情况下占用过多内存
3. **临时文件**: 虽然使用了 `TemporaryDirectory`，但在处理过程中可能同时存在多个大文件

### 3.2 资源限制

**当前配置**:
- 内存: 32GB
- CPU: 8 cores
- 超时: 24 小时

**问题**:
- 32GB 内存对于处理 540 个文件可能不够
- FFmpeg 使用 8 线程可能在某些情况下导致内存峰值过高

## 4. 解决方案建议

### 4.1 短期解决方案

1. **增加内存限制**
   - 将内存从 32GB 增加到 64GB 或更高
   - 修改 `.github/workflows/backend-deploy.yaml` 中的 `--memory` 参数

2. **优化 FFmpeg 参数**
   - 减少线程数：从 8 线程改为 4 线程
   - 降低内存使用：使用更低的 preset（如 `ultrafast`）

3. **分批处理**
   - 将 540 个文件分成多个批次处理
   - 每个批次处理完成后释放资源

### 4.2 长期解决方案

1. **内存管理优化**
   - 在处理每个文件后显式清理 Python 对象
   - 使用 `gc.collect()` 强制垃圾回收
   - 限制并发处理的文件数

2. **临时文件管理**
   - 在处理完每个文件后立即删除临时文件
   - 监控临时目录大小

3. **错误恢复机制**
   - 当检测到 `exit=-9` 时，记录失败并继续处理下一个文件
   - 不要因为单个文件失败而终止整个任务

4. **资源监控**
   - 在处理过程中监控内存使用
   - 当内存使用接近限制时，暂停处理或清理资源
