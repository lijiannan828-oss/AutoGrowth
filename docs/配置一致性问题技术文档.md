## 二、逐项分析

### 2.1 配置向导框架（任务 1.3.1）

**功能描述：** 实现左右结构页面，左侧步骤导航支持点亮、点击回退和重新尝试。

**一致性问题：**

- 步骤状态机一致性：用户在步骤间跳转时，已填写的配置数据可能与当前步骤不匹配
- 回退重填一致性：用户回退到第 N 步修改后，第 N+1 ~ 最后一步的依赖数据需要级联失效或重新校验
- 前后端状态同步：向导中间态是否需要持久化到后端，断线恢复时如何保证一致

**现状分析：**

当前 `StrategyForm.tsx` 使用 React Hook Form 管理表单，已有 AdSet → Ad 的单向联动（通过 `useWatch` 监听字段变化自动同步）。但缺乏多步骤向导的状态管理机制。

**建议方案：**

```
前端状态机模型：
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ Step 1  │───▶│ Step 2  │───▶│ Step 3  │───▶│ Step 4  │
│ 基础配置 │◀───│ 风格选择 │◀───│ 权重调整 │◀───│ 确认提交 │
└─────────┘    └─────────┘    └─────────┘    └─────────┘
                    共享 FormContext
```

1. 使用 React Context 维护全局向导状态，每步数据独立存储
2. 回退时标记后续步骤为 `dirty`，进入时触发重新校验
3. 每步完成时通过 Zod schema 做增量校验，确保数据合法性
4. 可选：关键步骤完成后调用后端 `/api/v1/config/draft` 持久化草稿

### 2.2 风格权重平衡（任务 1.3）

**功能描述：** 实现拖动式风格权重调整，主风格 ≥50%，辅助风格数值自动配平。

**一致性问题：**

- 数值约束一致性：所有风格权重之和必须恒等于 100%，主风格不得低于 50%
- 拖动过程中的中间态：拖动 A 风格时，B/C 风格需要实时重新分配，不能出现总和 ≠ 100% 的瞬间
- 前后端校验双重保障：前端拖动计算的结果提交到后端时，后端需要二次校验

**现状分析：**

当前 `storyline_engine.py` 中已有权重分配逻辑（场景权重按比例分配帧数），但这是后端处理逻辑，前端缺乏交互式权重平衡组件。

**建议方案：**

```typescript
// 权重自动配平算法伪代码
function rebalanceWeights(styles: Style[], changedIndex: number, newValue: number) {
  const PRIMARY_MIN = 50;
  // 1. 钳位：主风格不低于 50%
  if (changedIndex === 0) newValue = Math.max(newValue, PRIMARY_MIN);

  // 2. 计算剩余可分配额度
  const remaining = 100 - newValue;
  const others = styles.filter((_, i) => i !== changedIndex);
  const othersTotal = others.reduce((sum, s) => sum + s.weight, 0);

  // 3. 按比例缩放其他风格
  others.forEach(s => {
    s.weight = othersTotal > 0
      ? Math.round(remaining * (s.weight / othersTotal))
      : Math.round(remaining / others.length);
  });

  // 4. 修正舍入误差，差值加到最大的辅助风格上
  const actualTotal = styles.reduce((sum, s) => sum + s.weight, 0);
  if (actualTotal !== 100) {
    const maxOther = others.reduce((a, b) => a.weight > b.weight ? a : b);
    maxOther.weight += (100 - actualTotal);
  }
}
```

后端校验层（FastAPI）：

```python
@validator("style_weights")
def validate_weights(cls, weights: list[StyleWeight]):
    total = sum(w.value for w in weights)
    if abs(total - 100) > 0.01:
        raise ValueError(f"权重总和必须为 100%，当前为 {total}%")
    primary = next((w for w in weights if w.is_primary), None)
    if primary and primary.value < 50:
        raise ValueError("主风格权重不得低于 50%")
    return weights
```

### 2.3 风格 Seed 注入（任务 1.6）

**功能描述：** 将 33 套风格 Prefix 及 cover_prompt 批量落库，并实现 Backend 注入逻辑。

**一致性问题：**

- 批量写入原子性：33 条记录需要全部成功或全部回滚，不能出现部分写入的脏状态
- 幂等性保障：重复执行注入脚本时不应产生重复数据或覆盖用户已修改的自定义配置
- 前后端数据同步：落库后前端缓存需要失效刷新，否则展示的仍是旧数据

**现状分析：**

当前 `mappings.py` 中已有静态映射表（优化器、设计师、团队等），但风格数据尚未结构化入库。`config.py` 集中管理环境变量，Firestore 用于任务状态跟踪，但未用于风格配置持久化。

**建议方案：**

```python
# 批量注入服务 - 事务保障
async def seed_styles(db: AsyncSession, styles: list[StyleSeedData]):
    async with db.begin():  # 事务：全部成功或全部回滚
        for style in styles:
            existing = await db.execute(
                select(StyleConfig).where(StyleConfig.prefix == style.prefix)
            )
            row = existing.scalar_one_or_none()
            if row is None:
                db.add(StyleConfig(**style.dict()))
            elif not row.user_modified:  # 仅覆盖未被用户修改的记录
                for k, v in style.dict().items():
                    setattr(row, k, v)
        # 事务自动提交，失败自动回滚
```

前端缓存失效策略：

```typescript
// 注入完成后，通过 React Query 失效风格缓存
queryClient.invalidateQueries({ queryKey: ['styles'] });
```

### 2.4 分镜 1:1 绑定（任务 1.10.2）

**功能描述：** 实现 `shot_id` 与 `node_group_id` 的双向定位与强绑定协议。

**一致性问题：**

- 双向引用完整性：A 指向 B 的同时 B 必须指向 A，任何单边断裂都会导致数据不一致
- 级联操作一致性：删除一个 shot 时，对应的 node_group 绑定关系必须同步清除
- 并发修改冲突：两个用户同时修改同一 shot 的绑定关系时，需要冲突检测机制

**现状分析：**

当前 `storyline_engine.py` 中 `SceneSegment` 通过 `start_frame`/`end_frame` 定义片段范围，`reconstruct_storyline()` 将场景绑定到模板结构。但这是单向映射，缺乏 shot ↔ node_group 的双向强绑定机制。

**建议方案：**

```
双向绑定数据模型：

shots 表                    shot_node_bindings 表           node_groups 表
┌──────────┐               ┌─────────────────────┐         ┌───────────────┐
│ shot_id  │──────────────▶│ shot_id (FK, UNIQUE) │◀────────│ node_group_id │
│ ...      │               │ node_group_id (FK, U)│         │ ...           │
└──────────┘               │ bound_at             │         └───────────────┘
                           │ bound_by             │
                           └─────────────────────┘
                           UNIQUE(shot_id) + UNIQUE(node_group_id)
                           确保严格 1:1
```

关键约束：
1. 中间表 `shot_node_bindings` 对 `shot_id` 和 `node_group_id` 各加 UNIQUE 约束，数据库层面保证 1:1
2. 绑定/解绑操作封装在事务中，同时写入双方的 `bound_to` 冗余字段用于快速查询
3. 删除 shot 时通过 `ON DELETE CASCADE` 自动清除绑定记录

### 2.5 剧集批量创建（任务 1.9）

**功能描述：** 根据总集数批量生成 Episode 文件夹并自动绑定风格/资产引用。

**一致性问题：**

- 批量创建原子性：创建 N 个 Episode 文件夹时，部分失败会导致数量与预期不符
- 引用绑定一致性：每个 Episode 自动绑定的风格/资产引用必须指向真实存在的资源
- 编号连续性：批量创建的剧集编号必须连续且不与已有编号冲突

**现状分析：**

当前 `program_info.py` 模型中有 `episode_count` 字段，`generate.py` 支持批量生成最多 30 个广告。`ProgramBrowserTree.tsx` 实现了剧集目录树浏览。但缺乏批量创建 Episode 并自动绑定资产的完整流程。

**建议方案：**

```python
async def batch_create_episodes(
    db: AsyncSession,
    program_id: int,
    count: int,
    style_id: int,
    asset_ids: list[int]
):
    # 1. 查询已有最大编号，避免冲突
    max_ep = await db.execute(
        select(func.max(Episode.episode_number))
        .where(Episode.program_id == program_id)
    )
    start_number = (max_ep.scalar() or 0) + 1

    # 2. 预校验：风格和资产是否存在
    style = await db.get(StyleConfig, style_id)
    if not style:
        raise ValueError(f"风格 {style_id} 不存在")

    # 3. 事务内批量创建
    async with db.begin():
        episodes = []
        for i in range(count):
            ep = Episode(
                program_id=program_id,
                episode_number=start_number + i,
                style_id=style_id,
                folder_path=f"ep_{start_number + i:03d}/"
            )
            db.add(ep)
            episodes.append(ep)
        await db.flush()  # 获取生成的 ID

        # 4. 批量绑定资产引用
        for ep in episodes:
            for asset_id in asset_ids:
                db.add(EpisodeAsset(
                    episode_id=ep.id,
                    asset_id=asset_id
                ))
```

### 2.6 双向定位（任务 1.10.2.6）

**功能描述：** 实现表格行点击 → 面板节点聚焦，以及面板节点点击 → 表格行高亮的联动交互。

**一致性问题：**

- 双向选中态同步：点击 A 侧高亮 B 侧时，B 侧的高亮状态需要与 A 侧严格同步，不能出现"两边都高亮不同项"的状态
- 滚动定位一致性：聚焦目标元素时需要滚动到可视区域，滚动完成前不应触发新的联动事件
- 事件循环防抖：A 点击 → 高亮 B → B 的高亮变化又触发 A 的联动，形成死循环

**现状分析：**

当前 `StrategyForm.tsx` 已实现 AdSet → Ad 的单向联动，`SimpleStickerEditor.tsx` 支持拖拽时实时更新坐标。但缺乏双向联动的统一状态管理和防循环机制。

**建议方案：**

```typescript
// 双向定位 Hook - 防循环设计
function useBidirectionalFocus() {
  const [focusedId, setFocusedId] = useState<string | null>(null);
  const sourceRef = useRef<'table' | 'panel' | null>(null);
  const lockRef = useRef(false);

  const focusFromTable = useCallback((id: string) => {
    if (lockRef.current) return;     // 防循环锁
    lockRef.current = true;
    sourceRef.current = 'table';
    setFocusedId(id);
    requestAnimationFrame(() => {     // 下一帧解锁
      lockRef.current = false;
    });
  }, []);

  const focusFromPanel = useCallback((id: string) => {
    if (lockRef.current) return;
    lockRef.current = true;
    sourceRef.current = 'panel';
    setFocusedId(id);
    requestAnimationFrame(() => {
      lockRef.current = false;
    });
  }, []);

  return { focusedId, source: sourceRef.current, focusFromTable, focusFromPanel };
}
```

## 三、一致性保障通用策略

### 3.1 数据层

| 策略 | 适用场景 | 实现方式 |
|------|---------|---------|
| 数据库事务 | 批量写入（1.6 seed 注入、1.9 批量创建） | `async with db.begin()` 包裹所有写操作 |
| UNIQUE 约束 | 1:1 绑定关系（1.10.2 分镜绑定） | 数据库层面 UNIQUE 索引 |
| 外键 + CASCADE | 级联删除（1.10.2 绑定清理） | `ON DELETE CASCADE` |
| 乐观锁 | 并发修改检测 | `version` 字段 + `WHERE version = ?` |
| 幂等键 | 重复请求防护（1.6 重复注入） | `user_modified` 标记 + UPSERT |

### 3.2 前端层

| 策略 | 适用场景 | 实现方式 |
|------|---------|---------|
| Zod 双重校验 | 所有表单提交（1.3.1 向导、1.3 权重） | 前端 Zod schema + 后端 Pydantic validator |
| React Query 缓存失效 | 数据变更后刷新（1.6 注入后） | `invalidateQueries` 精确失效 |
| 防循环锁 | 双向联动（1.10.2.6 双向定位） | `lockRef` + `requestAnimationFrame` |
| 脏标记机制 | 向导回退（1.3.1 配置向导） | 步骤 `dirty` 标记 + 进入时重校验 |
| 实时约束计算 | 权重拖动（1.3 权重平衡） | `onChange` 内同步重算 + 舍入修正 |

### 3.3 接口层

| 策略 | 适用场景 | 实现方式 |
|------|---------|---------|
| 请求幂等 | 所有写操作 | 客户端生成 `idempotency_key`，后端去重 |
| 响应一致性 | 批量操作结果 | 返回 `{ success: [], failed: [] }` 明细 |
| 版本号校验 | 并发编辑 | 请求携带 `version`，后端比对后决定是否接受 |
