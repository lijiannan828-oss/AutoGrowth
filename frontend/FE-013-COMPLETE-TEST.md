# FE-013 下载功能优化完整测试指南

## 测试目标

验证 FE-013-1 至 FE-013-6 的所有功能是否正常工作，特别是 FE-013-6 的竞态条件修复。

## 测试前准备

### 1. 确认环境

```bash
# 检查前端服务是否运行
lsof -i :3001 | grep LISTEN

# 如果未运行，启动前端服务
cd frontend
npm run dev
```

### 2. 准备测试数据

选择一个包含大量文件的目录进行测试：
- **推荐**: 500+ 个文件，分布在多个子目录中
- **最小**: 至少 250 个文件（确保触发至少 2 个批次）

### 3. 打开浏览器开发者工具

1. 打开 Chrome/Edge 浏览器
2. 按 `F12` 打开开发者工具
3. 切换到以下标签：
   - **Console** - 查看日志
   - **Network** - 监控网络请求
   - **Performance** (可选) - 监控性能

## 测试步骤

### 阶段 1: 基础功能测试（FE-013-1, FE-013-2, FE-013-3）

#### 步骤 1.1: 测试目录句柄缓存（FE-013-1）

1. 访问：http://localhost:3001/pipeline/library
2. 选择一个包含多个子目录的剧集（如 5+ 个子目录）
3. 打开 Console，清空日志
4. 选择该剧集的所有文件，点击"下载"
5. 选择保存位置

**观察点**:
- 查看 Console 日志中的缓存相关日志：
  ```
  [Download] 创建/获取目录并缓存: {目录路径}
  [Download] 缓存命中: {目录路径}
  ```
- 统计：
  - "创建/获取目录并缓存" 应该出现 **目录数量** 次（不是文件数量）
  - "缓存命中" 应该频繁出现

**需要记录的信息**:
```
FE-013-1 测试结果:
- 总文件数: ___
- 目录数量: ___
- "创建/获取目录并缓存" 出现次数: ___
- "缓存命中" 出现次数: ___
- 缓存命中率: ___% (缓存命中次数 / (总文件数 - 目录数量))
```

#### 步骤 1.2: 测试 UI 渲染节流（FE-013-2）

1. 继续使用同一个下载任务
2. 观察 Console 日志中的更新频率

**观察点**:
- 查看 `updateTask` 调用频率
- 应该看到每 500ms 更新一次（2Hz）

**需要记录的信息**:
```
FE-013-2 测试结果:
- UI 更新频率: 约 ___ 次/秒（应该是 2 次/秒）
- 进度条是否流畅: 是/否
- 是否有卡顿: 是/否
```

#### 步骤 1.3: 测试并发控制（FE-013-3）

1. 继续使用同一个下载任务
2. 观察 Console 日志中的并发信息

**观察点**:
- 查看 "运行中" 数量，应该始终 ≤ 5
- 查看队列长度变化
- 查看任务完成后的补充逻辑

**需要记录的信息**:
```
FE-013-3 测试结果:
- 最大并发数: ___ (应该是 5)
- 队列管理是否正常: 是/否
- 任务完成后是否立即补充: 是/否
```

### 阶段 2: 分批获取测试（FE-013-4）

#### 步骤 2.1: 测试分批 URL 获取

1. **重要**: 在 Network 标签中设置网络节流：
   - 选择 "Fast 3G" 或 "Slow 3G"（模拟 API 延迟）
2. 选择一个包含 500+ 个文件的目录
3. 打开 Console，清空日志
4. 开始下载

**观察点**:
- 初始应该只获取第一批 URL（200 个文件）
- 当队列长度 < 50 时，应该触发获取下一批
- Network 标签中应该看到多个 `/pipeline/batch-urls` 请求

**需要记录的信息**:
```
FE-013-4 测试结果:
- 总文件数: ___
- 初始批次大小: ___ (应该是 200)
- 批次获取触发次数: ___
- Network 请求数量: ___
- 每个请求的文件数量: 约 ___ 个
```

### 阶段 3: 健壮性测试（FE-013-5）

#### 步骤 3.1: 测试网络错误重试

1. 在 Network 标签中选择 "Offline"
2. 开始下载文件
3. 等待几秒后，切换回 "Online"
4. 观察重试行为

**观察点**:
- 应该看到重试日志：
  ```
  [Download] FE-013-5: 网络请求失败: ... (已重试 3 次)
  ```
- 如果网络恢复，文件应该成功下载

**需要记录的信息**:
```
FE-013-5 网络重试测试结果:
- 是否看到重试日志: 是/否
- 重试次数: ___ (应该是 3)
- 网络恢复后是否成功: 是/否
```

#### 步骤 3.2: 测试失败文件列表弹窗

1. 模拟部分文件失败（可以通过网络错误或权限错误）
2. 等待下载完成
3. 观察是否显示失败文件列表弹窗

**观察点**:
- 下载完成后应该自动显示失败文件列表弹窗
- 弹窗应该显示失败文件数量和详细信息

**需要记录的信息**:
```
FE-013-5 失败文件弹窗测试结果:
- 失败文件数量: ___
- 弹窗是否自动显示: 是/否
- 失败文件信息是否正确: 是/否
```

#### 步骤 3.3: 测试导出和重试功能

1. 在失败文件列表弹窗中点击"导出失败日志"
2. 检查下载的文件内容
3. 点击"重试失败项"
4. 观察是否启动新的下载任务

**需要记录的信息**:
```
FE-013-5 导出和重试测试结果:
- 导出日志是否成功: 是/否
- 日志内容是否正确: 是/否
- 重试是否启动新任务: 是/否
```

### 阶段 4: 竞态条件修复测试（FE-013-6）⭐ **重点**

#### 步骤 4.1: 压力测试 - 快速下载 + 慢速 API

这是最关键的测试，用于验证竞态条件修复。

1. **设置网络节流**:
   - 在 Network 标签中选择 "Slow 3G"（模拟 API 延迟 2-3 秒）
2. **准备大量文件**:
   - 选择一个包含 500+ 个文件的目录
3. **开始下载**:
   - 打开 Console，清空日志
   - 开始下载
4. **观察关键日志**:
   - 查找 FE-013-6 相关日志
   - 特别关注等待日志

**关键观察点**:
- ✅ **应该看到等待日志**:
  ```
  [Download] FE-013-6: 等待中... (队列空闲但正在获取: true, 还有批次: true, 剩余路径: XXX)
  ```
- ✅ **不应该提前完成**: 即使队列为空，如果正在获取下一批，应该继续等待
- ✅ **完成日志应该显示所有条件**:
  ```
  [Download] FE-013-6: 所有下载任务已完成 (队列空闲: true, 未获取中: true, 无更多批次: true)
  ```

**需要记录的信息**:
```
FE-013-6 压力测试结果:
- 总文件数: ___
- 批次数量: ___
- 是否看到等待日志: 是/否
- 等待日志出现次数: ___
- 是否提前完成: 是/否 (应该是 否)
- 实际下载文件数: ___
- 期望下载文件数: ___
- 是否所有文件都下载: 是/否
```

#### 步骤 4.2: 验证完成条件

检查完成时的日志，确认所有条件都满足。

**需要记录的信息**:
```
FE-013-6 完成条件验证:
- 队列空闲 (pool.isIdle()): true/false
- 未获取中 (!isFetchingUrls): true/false
- 无更多批次 (!hasMoreBatches): true/false
- 所有条件都满足: 是/否
```
