# FE-013-4 分批 URL 获取测试指南

## 实现说明

已实现分批 URL 获取功能，避免在下载开始时一次性请求所有 URL，改为按需分批获取。

### 核心改进

1. **分批获取策略**:
   - 初始只获取第一批 URL（200 个文件）
   - 当队列长度 < 50 时，自动触发获取下一批（200 个文件）
   - 避免一次性请求大量 URL 导致的内存和网络压力

2. **动态队列管理**:
   - AsyncPool 支持队列低阈值回调
   - 自动监控队列长度，及时补充新任务
   - 避免 Worker 空转，保持下载连续性

3. **预加载优化**:
   - 预加载阈值（50）配合并发速度（5）调整
   - 确保在队列耗尽前获取下一批 URL
   - 避免下载中断

### 预期效果

- **内存使用**: 减少初始内存占用（不一次性加载所有 URL）
- **网络效率**: 分批请求，减少单次请求压力
- **下载连续性**: 队列及时补充，避免 Worker 空转
- **用户体验**: 下载开始更快，无需等待所有 URL 获取完成

## 测试步骤

### 1. 准备测试数据

选择一个包含大量文件的目录进行下载测试（建议 500+ 文件），这样可以明显观察到分批获取效果。

### 2. 开始下载

1. 打开浏览器开发者工具（F12）
2. 切换到 Console 标签
3. 切换到 Network 标签（用于监控网络请求）
4. 在资源库页面选择要下载的目录（500+ 文件）
5. 点击"下载"按钮
6. 选择保存位置

### 3. 观察控制台日志

在下载过程中，观察控制台输出：

**初始化日志**:
```

[Download] FE-013-4: 第一批获取成功，文件数量: 200

[Download] FE-013-4: 还有 300 个路径待获取，将在队列低于 50 时自动获取

**批次获取触发日志**（当队列长度 < 50 时）:
```

### 4. 验证分批获取

**检查点**:
- 初始只获取第一批 URL（200 个文件）
- 下载开始后，当队列长度 < 50 时触发下一批获取
- 网络请求应该分批进行，而不是一次性请求所有 URL

**Network 标签观察**:
- 应该看到多个 `/pipeline/batch-urls` 请求
- 每个请求的 payload 应该包含约 200 个路径
- 请求应该按时间顺序分批发出

### 5. 验证队列管理

**检查点**:
- 队列长度应该保持在合理范围（不会完全耗尽）
- 当队列长度 < 50 时，应该立即触发下一批获取
- 下载应该连续进行，不应该出现长时间等待

**示例日志序列**:
```
[Download] FE-013-3: 开始下载 - file1 (队列长度: 199, 运行中: 1)
...
[Download] FE-013-3: 开始下载 - file150 (队列长度: 50, 运行中: 5)
[Download] FE-013-3: 开始下载 - file151 (队列长度: 49, 运行中: 5)
[Download] FE-013-4: 队列长度低于阈值，触发获取下一批 URL  // 触发！
[Download] FE-013-4: 获取下一批 URL - 200 个文件 (剩余: 100)
[Download] FE-013-4: 批次获取成功 - 200 个文件 (总计: 400)
[Download] FE-013-4: 已添加 200 个新文件到队列
[Download] FE-013-3: 开始下载 - file152 (队列长度: 248, 运行中: 5)  // 队列已补充
```

### 6. 验证下载连续性

**检查点**:
- 下载应该连续进行，不应该出现长时间停顿
- Worker 不应该因为队列为空而等待
- 所有文件应该最终完成下载

## 故障排查

如果发现分批获取未生效：

1. **检查日志**: 确认是否看到"FE-013-4"相关日志
2. **检查初始批次**: 确认初始只获取了 200 个文件
3. **检查队列监控**: 确认队列长度监控是否正常工作
4. **检查触发条件**: 确认队列长度 < 50 时是否触发下一批获取

如果发现队列耗尽：

1. **检查阈值**: 确认 `QUEUE_LOW_THRESHOLD` 设置是否合理（当前为 50）
2. **检查批次大小**: 确认 `BATCH_SIZE` 是否足够（当前为 200）
3. **检查并发速度**: 确认并发数（5）和批次大小的比例是否合理
